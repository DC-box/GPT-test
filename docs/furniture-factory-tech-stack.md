# 家具厂核心管理模块技术栈与落地方案

## 1. 建设目标与系统边界

本方案面向家具厂的报价管理、入出库管理、库存管理和权限管理四个核心模块，覆盖板材、五金件、包装材料和成品家具等多类物料的日常业务。
系统目标是实现报价成本可核算、物料流转可追溯、库存状态可实时监控、权限操作可审计，并兼顾中小家具厂现有 Excel 台账迁移、人员信息化水平参差不齐和后续扩展对接的现实情况。

本项目定位为家具厂内部局域网系统，预计 3-5 名工作人员使用，核心诉求是老板能在办公室电脑上快速报价、仓库人员能录入入出库、库存能实时查询。因此本阶段建议优先建设轻量 Web 管理后台，不强制开发原生 App，也不建议一开始上云、上微服务或建设复杂监控平台。仓库、销售、采购、财务和总负责人均通过浏览器访问局域网服务器，移动端仅作为响应式页面补充。

## 2. 推荐开发栈

### 2.1 适配性结论

如果只服务于一个家具厂内部局域网、3-5 个工作人员使用，上一版“Vue + Spring Boot + PostgreSQL + Redis + MinIO + Nginx + Prometheus / ELK + 可升级 Kubernetes”的组合整体偏重。Vue、Spring Boot 和关系型数据库仍然适配，但 Redis、MinIO、Kubernetes、完整监控日志平台、短信服务商等不应作为第一期必选项。

本项目更适合采用“轻量单体应用 + 单机数据库 + 本地文件存储 + 局域网部署”的方案：功能上保留报价、入出库、库存和权限的完整闭环，技术上减少中间件数量，降低采购成本、运维复杂度和后续维护门槛。

### 2.2 第一推荐：轻量但可扩展的 Java 单体方案

| 层级 | 推荐技术 | 是否一期必选 | 选型说明 |
| --- | --- | --- | --- |
| 前端框架 | Vue 3 + TypeScript + Vite | 是 | 适合后台管理系统，页面开发效率高，后续也方便扩展移动端响应式页面。 |
| UI 组件 | Element Plus | 是 | 表单、表格、弹窗、上传、分页和权限菜单组件成熟，适合报价、入出库、库存台账页面。 |
| 表格增强 | vxe-table | 可选 | 如果 Excel 式批量编辑较多再引入；第一期普通 Element Plus 表格也能满足。 |
| 图表 | ECharts | 可选 | 老板看板、库存趋势和报价转化统计可在第二期加入。 |
| 后端框架 | Java 21 + Spring Boot 3 | 是 | 业务稳定、事务能力强，适合库存流水、权限审计和报价成本核算。 |
| ORM | MyBatis-Plus | 是 | 适合台账、报表和复杂筛选，开发效率高。 |
| 权限 | Spring Security + Session 或 JWT | 是 | 局域网内可优先使用服务端 Session，若未来对接移动端或外部 API 再使用 JWT。 |
| Excel 导入导出 | EasyExcel | 是 | 历史库存、材料价格、入出库明细和盘点单都需要批量导入导出。 |
| PDF 生成 | 后端 HTML 模板 + OpenHTMLToPDF | 是 | 报价单建议后端生成，保证老板打印和发客户时格式稳定。 |
| 数据库 | PostgreSQL 16 或 MySQL 8 | 是 | 3-5 人使用量不大，但库存系统要求事务可靠，仍建议使用成熟关系型数据库。若团队更熟 MySQL，可选 MySQL。 |
| 文件存储 | 服务器本地磁盘目录 | 是 | 报废照片、报价 PDF 和 Excel 文件直接存本机目录即可，无需第一期上 MinIO。 |
| 部署 | 一台办公室电脑 / 小型服务器 + Docker Compose | 是 | 在局域网固定 IP 访问，备份数据库和附件目录即可。 |
| 反向代理 | Nginx | 可选 | 若 Spring Boot 直接托管前端静态文件，可暂不使用；需要统一域名、HTTPS 或端口转发时再加。 |

### 2.3 第一阶段建议暂缓的技术

| 技术 | 暂缓原因 | 何时再引入 |
| --- | --- | --- |
| Redis | 3-5 人局域网访问并发很低，权限和会话可直接放数据库或内存，库存查询也不需要缓存。 | 多门店、多仓库或并发明显上升时。 |
| MinIO / 云对象存储 | 本地附件目录即可满足报废照片、报价 PDF 和导入文件存储。 | 附件很多、需要多服务器共享或异地备份时。 |
| Kubernetes | 单工厂单机部署没有必要，会显著增加运维复杂度。 | 多系统、多服务器、需要自动伸缩或高可用时。 |
| Prometheus + Grafana + Loki / ELK | 第一阶段可用应用日志文件和简单健康检查代替。 | 系统成为核心生产平台、需要长期性能监控和告警时。 |
| 短信服务商 | 局域网系统可先用站内预警、页面红点和库存预警列表。 | 老板需要离厂后仍接收缺货提醒时。 |

### 2.4 更低成本备选方案

如果预算非常有限，且确认未来 1-2 年都只在单厂、少量人员、局域网内使用，可以考虑 Python Django + PostgreSQL 或 Laravel + MySQL。这类方案开发速度快、后台管理和表单能力强，但如果后续要做更复杂的库存事务、审批流、对接 ERP 或长期企业级维护，Java + Spring Boot 的可持续性更好。

因此本项目的最终建议是：保留 Vue 3 + Spring Boot 3 + PostgreSQL / MySQL 的主干，去掉第一期非必要中间件，用单体应用和单机部署先把业务闭环跑通。


### 2.5 针对 C# + WinForm + MySQL 方案的适配性评估

如果项目范围明确收敛为“家具配件 + 原材料的极简进销存”，并且只在家具厂局域网电脑端使用，不做移动端、不做客户在线报价、不做多门店协同，那么 C# + WinForm + MySQL 是合适的，甚至比 Web 架构更贴近现场。它的优势是部署直观、电脑端表格录入体验好、与 Excel 批量导入导出结合紧密、开发人员可直接打包成安装程序交付，适合 3-5 名内部员工使用。

但需要注意，WinForm 方案更适合“内部工具型系统”，不适合一开始就承担复杂多端协同、远程访问、老板手机端审批、客户在线报价或多工厂统一管理。如果未来业务会扩展到移动端、跨厂区访问、与 ERP / 财务系统深度集成，Web 架构的扩展性会更好。

| 判断项 | C# + WinForm + MySQL 是否适合 | 建议 |
| --- | --- | --- |
| 使用人数 3-5 人 | 适合 | 并发压力很低，WinForm 直连后端服务或局域网服务均可。 |
| 只在电脑端操作 | 非常适合 | WinForm 的表格、快捷键、打印和 Excel 文件处理体验较好。 |
| 只管配件 / 原材料进销存 | 适合 | 功能边界清晰，不需要复杂前端工程化。 |
| Excel 批量交互 | 适合 | 可使用 NPOI 兼容 `.xls`，使用 EPPlus / ClosedXML 处理 `.xlsx`。 |
| 老板直接报价 | 基本适合 | 若报价只在办公室电脑使用，WinForm 可满足；若需要手机、平板或异地报价，Web 更合适。 |
| 多人同时操作库存 | 适合但要谨慎 | 必须通过事务和行锁处理采购入库、出库、盘点调整，避免负库存。 |
| 后续移动端 / 多工厂 | 不占优 | 这类需求建议优先 Web 架构，或把 WinForm 作为第一阶段临时内部工具。 |

该方案建议采用“三层逻辑 + 单数据库”的简化架构：WinForm 只负责界面展示、Excel 选择、录入确认和结果提示；业务逻辑层负责库存计算、导入校验、权限判断和操作日志；数据访问层统一封装 MySQL 事务，不允许界面层直接拼 SQL 修改库存。

推荐的 WinForm 技术栈如下：

| 层级 | 推荐技术 | 说明 |
| --- | --- | --- |
| 桌面端 | C# + WinForm + .NET 8 LTS | 如果团队已有 .NET Framework 经验，也可使用 .NET Framework 4.8，但新项目更建议 .NET 8。 |
| UI 控件 | 原生 WinForms DataGridView 起步，DevExpress 可选 | 预算有限先用原生控件；如果需要更好的表格筛选、打印和界面体验再购买 DevExpress。 |
| Excel | NPOI + ClosedXML / EPPlus | NPOI 兼容老 `.xls`，ClosedXML / EPPlus 处理 `.xlsx` 更方便。使用 EPPlus 时需确认商业授权。 |
| 数据访问 | Dapper 或 EF Core | 极简进销存用 Dapper 更轻、更可控；如果团队熟 EF Core，也可使用 EF Core。 |
| 数据库 | MySQL 8.0 InnoDB | 支持事务、行锁和索引，适合局域网小团队共享使用。 |
| 日志 | Serilog + 本地日志文件 + 操作日志表 | 程序异常写本地日志，业务关键操作写数据库操作日志。 |
| 部署 | 安装包 + 局域网 MySQL 服务 | 数据库集中部署在一台固定 IP 电脑 / 小服务器 / NAS，客户端安装 WinForm 程序。 |

需要对原架构图做两点修正。第一，不建议让每个 WinForm 客户端随意直连并分散处理库存更新逻辑；至少要把库存更新封装在统一业务类库和事务方法中。第二，库存台账不建议只保存一个“当前库存”结果，还应保留入库、出库、调整、盘点等流水记录，当前库存可由库存余额表维护并由流水追溯。

因此，若当前确定只做“配件 / 原材料极简进销存 + Excel 批量交互 + 局域网电脑端”，C# + WinForm + MySQL 可以作为第一阶段首选方案；若仍要覆盖完整报价管理、成品家具 BOM、移动端查看、后续多端扩展，则建议继续采用 Web 方案，或采用“WinForm 快速落地第一期，Web 作为第二期升级方向”。


### 2.6 两种方案的实现难度与工作量预估

以下周期按“1 名熟练全栈开发者主导开发 + 需求相对稳定 + 已有家具厂 Excel 样表 + 每周可获得业务确认”的前提估算。如果需要额外 UI 设计、复杂审批、多端适配、历史脏数据清洗或现场反复改流程，周期需要相应增加。

| 方案 | 适合范围 | 实现难度 | MVP 周期 | 可上线版本周期 | 主要工作量来源 |
| --- | --- | --- | --- | --- | --- |
| C# + WinForm + MySQL | 配件 / 原材料极简进销存、电脑端、Excel 批量导入导出、局域网使用 | 中低 | 2-3 周 | 4-6 周 | 表格界面、Excel 兼容、库存事务、导入校验、安装部署 |
| Vue 3 + Spring Boot + PostgreSQL / MySQL | 报价、BOM、入出库、库存、权限、审计、后续移动端或多端扩展 | 中高 | 4-6 周 | 8-12 周 | 前后端分离、权限体系、报价成本快照、库存流水、PDF、部署与备份 |

对当前“3-5 人、局域网、电脑端、只管配件 / 原材料、Excel 批量交互”的需求，我认为 C# + WinForm + MySQL 的第一版更容易做快、做稳。按我的实现能力，如果需求边界不扩大，MVP 可以在 2-3 周内完成：物料档案、供应商、采购入库、库存台账、Excel 导入导出、基础账号、操作日志和简单备份。再用 1-3 周做异常数据处理、权限细化、打印 / 导出格式、安装包、现场试用反馈修正，达到可上线版本。

Web 方案不是不能做，但工作量明显更大。它需要同时建设前端页面、后端接口、登录权限、接口鉴权、数据库迁移、静态资源部署和浏览器兼容。如果坚持覆盖报价、BOM、入出库、库存、权限和审计的完整闭环，MVP 通常需要 4-6 周，可上线版本更稳妥的周期是 8-12 周。

如果由我来推进，建议按以下节奏控制风险：

1. 第 1 周：确认 Excel 模板、物料字段、库存口径、入库 / 出库流程和报表样式，完成数据库表结构与主界面骨架。
2. 第 2-3 周：完成物料档案、采购入库、库存余额、库存流水、Excel 导入导出和基础查询，形成可演示 MVP。
3. 第 4 周：补充权限、操作日志、数据备份、异常提示、导入错误报告和安装包。
4. 第 5-6 周：用真实数据试运行，修正现场流程、打印导出格式、性能和易用性问题。

因此，若目标是尽快给家具厂内部用起来，我建议先做 WinForm 版极简进销存；若目标是长期产品化、后续要移动端、报价单在线流转或多工厂管理，再选择 Web 方案，或者先 WinForm 快速落地，再按实际使用反馈重构为 Web。

## 3. 总体架构设计

系统采用轻量前后端分离架构，也可以在部署时由 Spring Boot 直接托管前端打包后的静态文件。浏览器负责业务录入和查询展示，后端服务负责业务规则、权限校验、库存事务和报表生成，数据库负责持久化业务数据和审计数据。

建议后端采用模块化单体架构，不拆微服务。报价、库存、出入库和权限之间存在强事务关联，例如生产出库必须同步库存流水、销售报价需要读取材料价格和可用库存。模块化单体可以减少分布式事务和运维成本，最适合单工厂、少用户、局域网使用场景。

核心模块边界如下：

1. 基础资料域：材料档案、产品 BOM、客户档案、供应商档案、仓库档案和单位换算。
2. 报价域：报价单、报价明细、报价版本、报价模板、报价状态和成本快照。
3. 库存域：库存余额、库存流水、库存预留、安全库存、盘点单和盘点差异。
4. 入出库域：采购入库、退货入库、生产出库、销售出库、报废出库和单据附件。
5. 权限域：账号、角色、权限点、数据权限、登录日志和操作审计。
6. 通知域：库存预警、站内消息、短信发送记录和通知规则。

## 4. 核心业务建模建议

### 4.1 物料与 BOM

材料档案需要统一编码，建议编码规则为：物料类别 + 规格关键字 + 流水号。例如板材类可以使用 `BC-E0-KLB-1220-2440-001`，五金件可以使用 `WJ-HINGE-BRAND-001`。

BOM 应支持板材定制类和成品家具类两种结构。板材定制 BOM 需要记录基材、封边条、五金件、损耗率和加工费规则；成品家具 BOM 需要记录完整物料清单、单位用量、标准损耗和包装材料。

报价时应生成成本快照，保存当时的材料采购价、用量、损耗率、折扣和利润率。这样即使后续材料价格变化，也不会影响历史报价的追溯和版本对比。

### 4.2 库存余额与库存流水

库存设计建议采用“余额表 + 流水表”模式。余额表用于快速查询当前库存和可用库存，流水表用于审计追溯每一次入库、出库、盘点调整和报废。

可用库存建议计算为：当前库存 - 已预留库存 - 冻结库存。报价阶段可以只提示库存风险，不直接扣减库存；订单确认后再形成库存预留，生产或销售出库时正式扣减库存。

所有库存变动必须通过单据产生，不允许直接改库存余额。若确需修正，应通过盘点调整单或库存调整单完成，并记录审批人、原因和附件。

### 4.3 权限模型

权限模型建议采用 RBAC + 数据权限组合：RBAC 控制用户能访问哪些功能按钮和接口，数据权限控制用户能看到哪些物料类别、仓库、客户或业务部门数据。

预设角色包括总负责人、采购员、仓管员、销售员和财务。总负责人默认拥有全部权限，且可创建、禁用账号、配置角色和查看审计日志。仓管员默认只允许处理入出库、库存查询和盘点，不允许查看报价利润和材料成本敏感字段。

| `operation_log` | 操作审计 | 操作人、操作类型、对象、变更前后、IP、时间 |
| `login_log` | 登录日志 | 用户、登录时间、IP、设备、结果 |

## 6. 模块功能落地优先级

### 6.1 第一期：核心闭环上线

第一期目标是打通“基础资料 - 报价 - 入出库 - 库存 - 权限”的最小可用闭环。建议建设材料档案、仓库档案、客户档案、产品 BOM、材料价格、报价生成、采购入库、生产出库、销售出库、库存余额、库存流水、账号角色和基础权限。

验收重点包括：报价能自动读取 BOM 和材料价格，报价时能提示库存不足；入库和出库能实时生成库存流水并更新库存余额；总负责人能创建账号并分配预设角色；仓管员无法查看报价利润。

### 6.2 第二期：效率提升与追溯增强

第二期建议补充 Excel 批量导入、报价模板 PDF、报价版本回滚、退货入库、报废出库、报废照片上传、盘点单、库存预警和登录日志查询。

验收重点包括：历史库存和材料价格可批量导入；报价单可按模板导出 PDF；低于安全库存时产生站内消息和短信提醒；盘点后能自动生成账实差异。

### 6.3 第三期：经营分析与扩展集成

第三期建议建设经营看板、报价转化分析、材料损耗分析、供应商对账、采购建议、短信模板管理和外部系统 API。若后续接入财务系统、ERP 或生产排程系统，可基于已沉淀的单据和库存流水扩展。

## 8. 接口设计原则

接口应以业务单据为核心，不建议直接暴露库存余额修改接口。所有库存变化接口必须在同一数据库事务内完成单据状态变更、库存流水写入和库存余额更新。

报价相关接口需要保存成本快照，避免后续价格变化影响历史报价。权限相关接口必须记录操作审计，尤其是账号创建、禁用、权限调整、密码重置和数据权限变更。

建议接口路径按业务域组织。局域网部署时这些接口可以全部由同一个 Spring Boot 应用提供，例如：

- `/api/materials`：材料档案与材料价格。
- `/api/boms`：产品 BOM。
- `/api/quotes`：报价单与报价版本。
- `/api/inbounds`：入库单。
- `/api/outbounds`：出库单。
- `/api/stocks`：库存余额、库存流水和盘点。
- `/api/users`、`/api/roles`、`/api/audit-logs`：账号权限和审计。

## 9. 非功能要求

### 9.1 数据一致性

即使只有 3-5 人使用，库存扣减、库存预留和库存调整也必须使用数据库事务，并对同一材料和仓库的库存余额行加锁，避免老板报价、仓管出库、采购入库同时操作时造成负库存。对关键库存接口增加幂等号，避免重复提交导致库存重复扣减。

### 9.2 安全要求

密码必须使用强哈希算法保存，不能明文存储。JWT 应设置合理有效期，并支持账号禁用后令牌失效。报价利润、材料成本、权限配置和审计日志应作为高敏感权限点单独控制。

### 9.3 易用性要求

入库、出库和报价页面应优先支持键盘操作、材料名称联想、常用选项默认值和批量粘贴。Excel 导入必须提供错误行提示，例如材料编码不存在、单位不匹配或库存数量格式错误。

### 9.4 可维护性要求

后端按业务域拆包，避免所有逻辑堆叠在控制器中。核心库存计算、报价成本计算和权限判断应写入独立服务，并配套单元测试。数据库变更使用 Flyway 或 Liquibase 管理。

## 10. 开发与交付建议

建议采用两周一个迭代的敏捷交付方式。第一周完成页面原型、数据模型和核心接口，第二周完成联调、测试、导入模板和用户试用反馈修正。

推荐至少划分开发环境和生产环境；如果预算有限，测试环境可以用开发机或临时 Docker 环境代替。生产环境可部署在一台固定 IP 的办公室电脑、NAS 或小型服务器上，并配置每日数据库备份和附件目录备份。上线前必须完成初始库存导入、账号权限初始化、材料编码核对、报价模板确认和库存预警阈值配置。

## 11. 测试策略

1. 单元测试：覆盖报价成本计算、BOM 用量计算、库存可用量计算和权限判断。
2. 集成测试：覆盖采购入库、生产出库、销售出库、盘点调整和报价确认后的库存预留。
3. 权限测试：验证采购员、仓管员、销售员、财务和总负责人各自的菜单、按钮和数据范围。
4. 导入测试：验证历史库存、材料价格和入库明细 Excel 导入的成功、失败和错误提示。
5. 并发测试：验证多人同时出库、重复提交和库存不足场景，确保不会出现负库存。
6. 验收测试：使用家具厂真实样例数据验证报价单、入出库单、库存查询和权限审计。

## 13. 关键风险与应对

| 风险 | 表现 | 应对策略 |
| --- | --- | --- |
| 物料编码不统一 | 同一种板材被录入多个名称 | 上线前统一材料编码，并在录入时做名称联想和重复校验。 |
| 库存初始数据不准 | 系统库存与实际库存不一致 | 上线前组织一次分仓盘点，以盘点结果作为初始化数据。 |
| 报价成本变化频繁 | 材料采购价变化影响报价稳定性 | 报价单保存成本快照，并设置材料价格生效日期。 |
| 权限配置过细导致难用 | 总负责人配置成本高 | 先提供预设角色，再开放自定义权限。 |
| 仓库人员录入习惯差异大 | 入出库漏录或重复录入 | 简化页面、提供扫码或联想、关键操作增加确认和幂等控制。 |

## 14. 结论

针对单个家具厂内部局域网、3-5 名工作人员使用的实际情况，如果系统范围是完整报价、BOM、入出库、库存、权限和后续扩展，本项目建议采用 Vue 3 + TypeScript + Element Plus 的前端后台技术栈，配合 Java 21 + Spring Boot 3 + PostgreSQL / MySQL 的轻量单体后端与数据架构。若系统范围进一步收敛为“家具配件 + 原材料极简进销存、电脑端操作、Excel 批量交互”，C# + WinForm + MySQL 也是合适甚至更轻的第一阶段方案。第一期不建议引入 Redis、MinIO、Kubernetes、复杂监控平台和短信服务，除非现场已有相应基础设施或明确提出远程通知、高可用、多服务器部署需求。

该方案能够在控制开发和运维成本的同时，满足老板快速报价、仓管入出库、库存实时查询和总负责人权限统管的核心需求，并为后续 ERP、财务、生产排程、移动端应用或多工厂管理预留扩展空间。
